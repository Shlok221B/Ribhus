Ribhus Platform Guide

Version: 0.1.0

Audience: You — so you never lose the plot on what Ribhus is, what each piece does, and how a request actually moves through the system.

Stack snapshot: Python 3.11+ · Typer CLI · FastAPI dashboard · React/Vite UI · Playwright Chromium · SQLite/JSON under .ribhus/ · OpenAI-compatible LLMs (OpenAI / OpenRouter / Ollama)

This document is the map of the running product today, not a wishlist. Deferred work (Stop button, fingerprint approvals, routines, vault) lives in docs/blueprint-gap-tasks.md.

1. What Ribhus is (one paragraph)

Ribhus is a local-first AI agent you run on your machine. You talk to it in natural language (CLI or web dashboard). It plans, calls tools (search, browser, files, shell, WhatsApp Web, Gmail Web, maps, MCP…), remembers preferences, and asks before consequential sends. You pick the model. India-focused skills (company research, travel, football) plug in as packages. Multiple named bots can chat with you, run in parallel, and hand work to each other.

It is not a hosted cloud computer, not the official WhatsApp/Gmail APIs, and not Cursor/Grok Bot — even when some UX ideas look similar.

3. How a single turn actually runs

  1. Input — user prompt (CLI string, chat message, or task create).
  2. Context pack — system prompt + optional bot role + matched skills + memory snippet + history.
  3. Model call — OpenAI-compatible chat with tool schemas.
  4. Tool calls — for each call: preflight → PolicyEngine.authorize → execute → string result back into messages.
  5. Repeat until the model returns plain text or hits max_iterations.
  6. Persist — memory episode / prefs; dashboard task status + typed events; chat message.
# Conceptual core (see Agent.run in src/ribhus/agent/loop.py)
while not state.finished and state.iterations < max_iterations:
    response = await model.generate(messages=state.messages, tools=tool_schemas)
    if response.has_tool_calls():
        for call in response.tool_calls:
            result = await tools.execute(call.name, call.arguments)  # policy inside
            state.add_tool_result(call.id, result)
    else:
        state.finish(response.text)

7. Agent core

7.1 System prompt — agent/state.py

SYSTEM_PROMPT is a long standing instruction: how to use tools, WhatsApp vs email channel choice, maps/near-me rules, never ask send approval in chat (CLI/dashboard cards handle it), prefer todo for multi-step work, etc.

AgentState holds messages, iterations, final text, helpers to append tool results.

7.2 Loop — agent/loop.py · class Agent

Constructor: model, tools, max_iterations, system_prompt, on_event callback, skill addon, memory, todo store.

Main method: async def run(prompt, history=None) -> AgentState

Important helpers in the same file:

FunctionJob
prefers_whatsapp_channel / prefers_email_channelHeuristics so “message Rahul” doesn’t become Gmail
looks_whatsapp_read_onlySummary asks → block accidental whatsapp_send
asks_send_approval_in_chatDetects bad “please approve?” prose → nudge
send_tool_nudge_for_promptSoft redirect to the right send tool
_trim_historyCap message list

Plan integration comes from agent/plan_loop.py: looks_multi_step, todo nudges, verify after consequential tools (email_send, whatsapp_send, file writes).

7.3 Events the agent emits

Via on_event: thinking, skill, tool_start, tool_end, plan, done.

Dashboard TaskStore normalizes aliases to typed events (tool.started, turn.completed, …) — see §12.

8. Models — talking to an LLM

Files: models/base.py, models/openai_compatible.py

@dataclass
class ToolCall:
    id: str
    name: str
    arguments: dict[str, Any]

@dataclass
class ModelResponse:
    text: str | None
    tool_calls: list[ToolCall]
    raw: Any

OpenAICompatibleModel wraps the OpenAI Python SDK against any OpenAI-compatible base URL (OpenAI, OpenRouter, Ollama). It exposes generate(messages, tools=...).

There is no separate Anthropic adapter yet — anything that speaks the OpenAI chat+tools shape works.

17. Job hunt

Package: src/ribhus/jobs/ · UI: web/src/pages/JobHuntPage.tsx · API: web/routers/jobs.py

Pipeline:

  1. Save base LaTeX resume
  2. Connect Gmail (same profile as email channel)
  3. Paste job URL or description (single or batch)
  4. extract posting → tailor resume (model) → compile PDF via Tectonic
  5. Review draft email + PDF → explicit send approval → GmailSender

21. End-to-end example walks

A. CLI company research

uv run ribhus "Research this Indian company: Zoho"
  1. Skill company-research matches triggers → instructions injected
  2. Agent uses web_search / web_extract / maybe browser
  3. Returns sourced brief; episode saved to memory

B. Dashboard bot DM + WhatsApp send

  1. Create bot “Ops” with a job description
  2. Open /bots/:id, type: message Rahul on WhatsApp that dinner is at 8
  3. Orchestrator queues job → Agent calls whatsapp_send
  4. Task status awaiting_approval → you Approve/Edit/Deny in UI
  5. Send executes only if approved; approval.resolved event logged

C. Group handoff

  1. Create group with Researcher + Writer
  2. @Researcher find three hotels in Goa under 8k
  3. Researcher finishes → message_bot to Writer
  4. Writer’s queue wakes; reply may appear in both chats

D. Job hunt

  1. Dashboard → Job hunt → upload .tex → Connect Gmail
  2. Paste posting → tailor + compile PDF
  3. Check approval → send

26. Closing

Ribhus is a single agent runtime with three skins (CLI, dashboard, WhatsApp inbox), a policy gate, local memory, installable skills, browser-based Indian/daily channels, and a growing multi-bot layer. Everything durable lives under .ribhus/. Everything smart is an LLM + tools loop. Everything dangerous stops for a human.

When you add a feature: decide whether it is a tool, a skill, a channel, a bot orchestration change, or a dashboard API/UI change — then put it in the matching folder above.

Generated for local orientation. Re-read the source if behavior and this guide disagree — the code wins.
